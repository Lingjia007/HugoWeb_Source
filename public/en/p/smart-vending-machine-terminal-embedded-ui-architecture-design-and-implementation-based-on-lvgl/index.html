Smart Vending Machine Terminal: Embedded UI Architecture Design and Implementation Based on LVGL

A complete smart vending machine terminal UI system design based on ArtInChip platform + LVGL v8 + RT-Thread, covering composite pattern UI tree, event-driven architecture, Flex/Grid layout framework, dual payment modes (QR code display/camera scanning), UART3 serial communication protocol, Web WiFi AP configuration, DVP camera zero-copy preview, and other core technologies

Preface

In IoT terminal devices, interaction experience is often the key to product competitiveness. This article introduces the complete design and implementation of a smart vending machine terminal UI system based on ArtInChip embedded platform + LVGL v8 + RT-Thread. The project consists of a static UI skeleton generated by AiUIBuilder v2.0.2 combined with hand-written dynamic business logic, achieving a smooth transition from a WYSIWYG visual prototype to an interactive dynamic application.

1. System Architecture

1.1 Project Composition

The project is divided into two major modules:

Directory Responsibility Source
ui_builder/ Screen layout, static widgets, styles and fonts AiUIBuilder auto-generated
my_custom_init/ Interaction logic, data binding, communication and dynamic loading Hand-written

The module hierarchy within my_custom_init/:

Layer Module Responsibility
Infrastructure event_bus Pub-Sub decoupled communication
Infrastructure async_loader Worker thread + LVGL timer callback
Layout Framework layout_node Composite pattern UI node tree
Layout Framework layout_strategy Flex/Grid layout strategy mapping
Component Factory component_factory Assemble complete UI components
Component Factory widget_factory Register/create widgets by type name
Widget banner_carousel / banner_item Banner carousel controller
Widget commodity_card Product display and add-to-cart
Widget cart_item Shopping cart state management
Widget navi_item Navigation bar tab
Business custom_init Assemble all modules
Business web_config WiFi AP + HTTP configuration page
Business uart3_payment UART3 communication + payment flow
Business qr_scanner DVP camera + quirc decoding

1.2 Design Patterns

The project employs several classic design patterns:

  • Composite Pattern: layout_node framework unifies Container and Widget into a tree structure, implementing depth-first destruction via destroy() virtual function.
  • Factory Pattern: widget_factory registers creation functions by type name string, supporting dynamic creation of four widget types.
  • Pub-Sub Pattern: event_bus implements a lightweight event bus for decoupled communication between components.
  • Strategy Pattern: layout_strategy_t encapsulates layout types and parameters, mapping to LVGL Flex API calls.
  • Object Pool Pattern: Uses RT-Thread memory pools (rt_mp_create/rt_mp_alloc/rt_mp_free) for high-frequency widget data allocation, avoiding memory fragmentation.

2. Event-Driven Architecture

2.1 Event Bus Design

event_bus maintains a s_slots[EVT_TYPE_MAX] array, each slot supporting up to 8 subscribers, with RT-Thread mutex for thread safety.

typedef struct {
    event_handler_t handler;
    void *user_data;
} subscriber_t;

static event_slot_t s_slots[EVT_TYPE_MAX];

event_bus_publish() snapshots the subscriber list before releasing the lock and invoking callbacks, preventing iteration issues from subscription modifications within callbacks.

2.2 Core Event Flow

Eight event types are defined: cart add/remove/count change/price change, banner/commodity/navi config change, navi click.

Typical event flows:

  1. Add to Cart: commodity_card click add button → publish EVT_CART_ITEM_ADDED → cart_item module subscribes → publish EVT_CART_COUNT_CHANGED + EVT_CART_PRICE_CHANGED
  2. Cart Quantity Change: +/- button click → modify count → update total price label and count badge
  3. Web Config Change: HTTP POST → set pending flag → LVGL timer polls → publish EVT_BANNER_CONFIG_CHANGED etc. → components hot-update
  4. Navigation Click: navi_item click → publish EVT_NAVI_ITEM_CLICKED

2.3 Cross-Thread Communication

Communication Path Mechanism Description
UART3 RX thread → LVGL thread Lock-free SPSC ring queue + LVGL timer (100ms) RX thread only parses and enqueues frames, never calls LVGL API
Web config thread → LVGL thread volatile flag + buffer + LVGL timer (200ms) HTTP thread only writes buffer, timer publishes events in LVGL thread
QR scan thread → UART3 rt_device_write() Thread-safe serial write

3.3 Screen Layout

800×480 screen divided into four zones:

Zone Position Size Component
Banner Carousel (153, 12) 494×78 banner (flex-row, horizontal scroll)
Navigation Bar (16, 102) 768×45 navi (flex-row, non-scrollable)
Product Display (0, 150) 800×220 commodity (grid 3 columns, vertical scroll)
Cart Panel (0, 70/480) 800×410 cart (flex-column, vertical scroll)

3.4 Animation Effects

  • Button Scale Animation: Zoom from 256 to 210 on click, using lv_anim_path_overshoot bounce, 100ms press + 200ms rebound.
  • Cart Panel Slide: Y coordinate animates from 480 (off-screen) to 70 (visible), 400ms linear, with opacity fade.
  • Carousel Page Turn: lv_obj_scroll_to_x animation, 600ms ease_out.

4. Banner Carousel Module

4.1 Architecture

The carousel module uses a controller-view separation design:

  • banner_types.h: Pure data type definitions, no UI dependency
  • banner_carousel: Does not create or own containers and child widgets, only attaches controller behavior
  • banner_item: Simple image widget, allocated from memory pool

4.2 Core Features

  • Auto-scroll: Timer-driven, pausable/resumable
  • Swipe Gesture Detection: Based on scroll_begin_cb / scroll_end_cb, comparing scroll_x delta against switch_threshold
  • Indicator Dots: Created with 50ms delay to avoid position errors from incomplete layout
  • Data Hot-Update: banner_carousel_update_data() pauses timer → clears children → rebuilds → rebuilds dots → resumes timer

5. Shopping Cart System

5.1 Commodity Card

Each card contains: product image (80×80), name label, price label, add-to-cart button, badge tag (best seller / new / recommended).

commodity_card_batch_update() implements differential update: add/remove cards as needed, then update data one by one, supporting Grid layout auto-wrapping. Memory pool capacity = COMMODITY_MAX_COUNT (30).

5.2 Cart Item

  • cart_add_commodity() searches existing items by name first; if found, increments count; otherwise creates new item
  • Automatically removes when count reaches 0, publishing EVT_CART_ITEM_REMOVED
  • cart_update_total_price() iterates all items, parses price strings (skipping currency prefix), calculates count * price_val sum
  • cart_update_count_tag() manages the count badge on the cart icon

6. UART Payment Flow

6.1 Frame Protocol 

1

AA 55 CMD LEN_H LEN_L DATA... 0D 0A
Direction CMD Name Data
PC → Device 0x01 CMD_QR_URL QR code URL (UTF-8)
PC → Device 0x02 CMD_PAY_STATUS Payment status code (1 byte)
PC → Device 0x03 CMD_ORDER_NO Order number (UTF-8)
PC → Device 0x04 CMD_HEARTBEAT_ACK Heartbeat ACK
Device → PC 0x81 CMD_REQ_QR name\0amount
Device → PC 0x82 CMD_REQ_QUERY Empty
Device → PC 0x83 CMD_REQ_CLOSE Empty
Device → PC 0x84 CMD_HEARTBEAT Empty
Device → PC 0x85 CMD_BARCODE_PAY auth_code\0[amount\0][subject]

6.2 Dual Payment Modes

Mode 1: User Scans QR Code

  1. User clicks settlement button → parse cart total → show payment mode selection dialog
  2. User selects “User Scan” → send CMD_REQ_QR to PC
  3. PC generates Alipay sandbox order, returns CMD_QR_URL
  4. Device displays QR code overlay (240×240, LVGL lv_qrcode widget)
  5. PC polls payment status and returns CMD_PAY_STATUS
  6. Success: show “Payment Successful!”, auto-hide after 2 seconds, clear cart, restore carousel

Mode 2: Device Scans Barcode

  1. User selects “Device Camera Scan”
  2. Start DVP camera + quirc scanning thread
  3. Set UI layer alpha=128 for video layer transparency
  4. quirc scans 18-28 digit numeric strings (payment auth codes), sends via CMD_BARCODE_PAY to PC
  5. PC calls Alipay barcode payment API, returns payment status
  6. Success flow same as above

6.3 Thread Safety

UART3 RX thread strictly never calls any LVGL API. After frame parsing, it only enqueues to the SPSC ring buffer. LVGL timer (100ms) dequeues and processes in the LVGL thread context.

7. QR Code Scanner Module

7.1 Hardware Configuration

  • DVP camera (OV5640), forced QVGA 320×240 output, reducing memory usage (~460KB)
  • ArtInChip video input framework (mpp_vin, drv_dvp)
  • Framebuffer video layer (mpp_fb) for camera preview
  • quirc QR code decoding library

7.2 Scanning Flow

  1. qr_scanner_start(): Initialize DVP (with 5-retry tolerance), configure sensor format, create quirc instance (160×120, 2x downsampling)
  2. Scan thread loop: dq_buf → discard first few frames → extract Y channel every 5 frames and downsample → quirc_decode
  3. handle_qr_result(): Detect payment auth codes (18-28 digit numeric), 5-second same-code cooldown, call uart3_payment_send_barcode()

7.3 Camera View Mode

Direct display of DVP captured frames via ArtInChip framebuffer video layer:

  • qr_scanner_start_camera_view(): Open framebuffer, set UI layer alpha=128
  • Zero-copy push of DVP buffers to video layer for high-performance picture-in-picture
  • Strict shutdown order: clear flag → stop scan thread → stop DVP stream → wait thread exit → disable video layer + restore UI alpha → release resources

7.4 Memory Management

  • Grayscale buffer allocated from CMA: aicos_malloc(MEM_CMA, scan_w * scan_h)
  • Downsampling: 2×2 area averaging, reducing 320×240 to 160×120 for quirc processing
  • DVP buffer released immediately after Y channel extraction

8. Web Configuration System

8.1 Architecture

Device starts WiFi AP (SSID: AIC-Banner-Config, password: 12345678, channel 6), IP 192.168.1.1, runs DHCP server and Mongoose HTTP server on port 80.

8.2 API Endpoints

Method Path Function
GET / Embedded HTML configuration page
GET /api/config Get banner config JSON
GET /api/commodity Get commodity config JSON
GET /api/navi Get navigation config JSON
POST /api/config Update banner config
POST /api/commodity Update commodity config
POST /api/navi Update navigation config
POST /api/reset Reset to default config
POST /api/upload/{filename} Upload banner image (validates 494×78)
POST /api/upload/commodity/{filename} Upload commodity image (validates 80×80)

8.3 Security Measures

  • Filename whitelist validation: only alphanumeric, ., _, -, max 64 characters
  • Early Content-Length rejection: return 413 if oversized
  • Receive buffer limit: force close connection when recv_mbuf.len > 307200 + 4096
  • Image dimension validation: parse PNG/JPEG/BMP file headers to verify dimensions
  • Price format validation: support multiple currency prefixes

8.4 Config Hot-Update

  1. HTTP thread receives POST → parse JSON → write to s_pending_json buffer → set flag
  2. Save JSON to SD card for persistence
  3. LVGL timer polls every 200ms → detect flag → publish events → components hot-update

9. Async Loading Mechanism

Implemented based on RT-Thread thread + dual message queues:

Main Thread (LVGL)          Worker Thread
    |                            |
    | submit(task)               |
    | ----[task_mq]---->         |
    |                            | work_fn(arg) → result
    |                     [result_mq]----> done_cb(result)
    |                            |
    | poll() <-- drain result_mq |
  • Worker thread stack: 4096 bytes, priority 20
  • Task/result queue capacity: 8 entries
  • async_loader_poll() called in LVGL timer, ensuring done_cb executes safely in LVGL thread

10. System Initialization Flow

custom_init() is the system assembly entry point, executing the following initialization sequence:

  1. Initialize infrastructure: event_bus, async_loader
  2. Initialize all widget module object pools
  3. Wait for SD card mount (max 50 retries, 100ms each)
  4. Copy default image resources from /rodata/image to /sdcard
  5. Initialize TTF fonts (Source Han Sans 15/18pt)
  6. Register four widget types to widget_factory
  7. Delete AiUIBuilder-generated static widgets, replace with dynamic components
  8. Create four major components (banner, commodity, cart, navi)
  9. Bind cart animation, settlement button events
  10. Subscribe to Web config change events
  11. Start Web config server, UART3 payment module, QR scanner module
  12. Load persistent config (override defaults)

11. Technical Highlights

  1. AiUIBuilder + Custom Code Bridge: layout_container_wrap() wraps tool-created LVGL objects as dynamic layout containers, retaining WYSIWYG prototyping capability while gaining runtime flexibility.

  2. Full Event-Driven Architecture: Zero direct dependencies between components. Cart doesn’t know about commodity cards, payment module doesn’t know about cart, Web config doesn’t know any UI component API.

  3. Embedded Web Configuration: Mongoose HTTP server + WiFi AP on RT-Thread. Connect phone to hotspot to modify config without firmware upgrade, auto-persisted to SD card.

  4. Dual Payment Modes: Support “user scan” and “device scan” modes via UART3 communication with PC host, implementing complete payment loop with Alipay sandbox.

  5. Lock-Free Inter-Thread Communication: SPSC ring queue for UART3, volatile flag + buffer for Web config, avoiding heavyweight lock overhead.

  6. Memory Pool Management: All high-frequency create/destroy widgets use RT-Thread memory pools with capacity aligned to business limits, avoiding fragmentation.

  7. Camera View Hardware Acceleration: Zero-copy DVP buffer push to video layer, UI layer semi-transparent for picture-in-picture effect.

  8. Composite Pattern UI Tree: Container and Widget unified as tree structure, supporting depth-first destruction, batch update, dynamic add/remove, making runtime hot-updates simple and reliable.
